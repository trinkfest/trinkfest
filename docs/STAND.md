# TrinkFest – Code-Stand (Sync zwischen allen Chats)

Diese Datei ist die zentrale Stelle für den aktuellen Code-Stand. Jeder Chat im Projekt TrinkFest arbeitet danach:

1. **Vor jeder Code-Arbeit:** diese Datei und den aktuellen Code unter `code/` lesen – nie aus einer älteren Chat-Version weiterbauen.
2. **Nach jeder Code-Änderung:** die geänderten Dateien unter `code/` komplett überschreiben und unten im Änderungsprotokoll einen Eintrag ergänzen (Datum, was geändert wurde, aus welchem Chat-Thema). Die Datei vorher frisch lesen, weil andere Chats sie parallel ändern.
3. Wenn der Code in GitHub (Repo „trinkfest“) neuer ist als hier: zuerst die aktuelle Datei von Timon hochladen lassen bzw. aus GitHub holen und hier aktualisieren.
4. **Ältere Details** (v103 und früher, Duelle-Entwicklung v84–v96, altes Änderungsprotokoll) stehen in `code/STAND-archiv.md`. Hier nur die aktuellen Dinge halten; wird diese Datei zu lang, ältere Einträge ins Archiv verschieben.
5. **Timon aktualisiert seine App, indem er den Ordner `trinkfest` am Mac ersetzt** (er kennt die Patch-Dateien nicht und braucht sie nicht). Deshalb bei jeder Änderung die **komplette `trinkfest-github.zip`** schicken (SendUserFile) und in einem Satz sagen, welche Dateien neu/geändert sind. Nur `index.html` reicht nicht, sobald `iap.js`, `scripts/*`, `config.js` oder `licenses-extra/` betroffen sind. Seine `config.js` nicht blind überschreiben, wenn er dort eigene Werte hat (`TF_IAP_CFG` am Ende ergänzen). Seine `package.json` kann ersetzt worden sein; fehlen dann Pakete (Fehler „could not determine executable to run“): `npm install @capacitor/core @capacitor/cli @capacitor/ios @capacitor/haptics @capacitor-community/admob @capgo/native-purchases @supabase/supabase-js @fontsource/montserrat`, dann `npm run ios`. Sein Ordner heißt derzeit `trinkfest-github (1)`, enthält `ios`, `node_modules`, `www`.
6. **Apple-Design-Durchgang (14.11., Patches 133–141):** Fortschritt, Regeln und Testmethode stehen in `code/STAND-apple-design.md` – dort zuerst lesen, bevor an Optik/Animationen gearbeitet wird. Lehre daraus: Ein `MutationObserver`, der auf dem beobachteten Element `classList.remove()` ruft, erzeugt auch ohne Änderung neue Records → Endlosschleife; immer erst mit `contains` prüfen.
